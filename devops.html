DevOps

A culture and set of practices uniting development and operations to deliver software faster and more reliably

Overview

DevOps is a way of working that breaks down the traditional wall between software development (Dev) and IT operations (Ops). Rather than developers "throwing code over the fence" to a separate team to run, DevOps brings them together with shared ownership, automation and fast feedback. The goal is to release software more frequently, more reliably and with less risk. It is as much a cultural shift as a technical one — collaboration, accountability and continuous improvement matter as much as any particular tool.

Core Principles

  • Collaboration & shared ownership — Dev and Ops are responsible for the service end to end ("you build it, you run it").
  • Automation — automate building, testing, deployment and infrastructure to remove slow, error-prone manual steps.
  • Continuous feedback — measure and monitor everything, and feed lessons straight back into the next change.
  • Small, frequent changes — ship in small increments to reduce risk and make problems easier to isolate.
  • Continuous improvement — treat failures as learning, with blameless post-incident reviews.

The DevOps Lifecycle

DevOps is often drawn as a continuous loop rather than a straight line, reflecting that delivery never really "finishes":

Stage Focus
Plan & Code Define work and write software, tracked in version control
Build & Test Compile and automatically test every change
Release & Deploy Promote changes to production safely and repeatably
Operate & Monitor Run the service, observe it, and feed insight back to planning

Key Practices & Tooling

  • Version control — Git is the foundation; all code and configuration lives here.
  • CI/CD pipelines — automated build, test and deployment on every change.
  • Infrastructure as Code (IaC) — define servers and services in code (e.g. Terraform) for consistent, repeatable environments.
  • Containers & orchestration — Docker and Kubernetes for portable, scalable deployment.
  • Configuration management — tools such as Ansible to enforce desired state.
  • Monitoring & observability — metrics, logs and traces (e.g. Grafana, Datadog) to understand live systems.

Measuring DevOps (DORA Metrics)

The widely used DORA metrics give a balanced view of both speed and stability, avoiding the trap of optimising one at the expense of the other:

  • Deployment frequency — how often you release.
  • Lead time for changes — how quickly a change goes from commit to production.
  • Change failure rate — what proportion of changes cause problems.
  • Mean time to restore — how fast you recover when something breaks.

Related Approaches

DevSecOps extends the model by building security into the pipeline from the start ("shift left") rather than bolting it on at the end. Platform engineering is a more recent evolution, where a dedicated team builds an internal platform and self-service tooling so product teams can ship safely without each reinventing the plumbing. Site Reliability Engineering (SRE), originating at Google, applies an engineering discipline to operations using concepts such as error budgets.

IT Director Considerations

  • DevOps is primarily a cultural and organisational change; tools alone will not deliver it
  • Investment in automation, skills and platform capability pays back in speed and reliability
  • Balancing delivery speed against governance, audit and change-control obligations
  • Embedding security (DevSecOps) rather than treating it as a final gate
  • Using outcome metrics (DORA) rather than vanity activity measures
  • Avoiding "DevOps in name only" — renaming a team without changing how it works

DevOps vs Traditional IT Delivery

Traditional delivery tends to separate development from operations, batch up large releases, and rely on manual hand-offs and change gates — which makes releases infrequent, high-risk events. DevOps favours shared ownership, automation and small, frequent changes, so releasing becomes routine and low-drama. It pairs naturally with Agile (which focuses on how work is planned and built) by extending the same fast-feedback philosophy all the way through to running software in production.
