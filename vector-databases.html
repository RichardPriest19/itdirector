Vector Databases

Databases built to store and search high-dimensional vectors by similarity

Overview

A vector database is a database designed to store embeddings — the numerical vectors that represent the meaning of text, images and other data — and to search them by similarity rather than exact match. Where a traditional database answers "find the row where this field equals that value", a vector database answers "find the items most similar in meaning to this one". This capability is what makes semantic search and retrieval-augmented generation (RAG) practical at scale, which is why vector databases have become a core part of the AI application stack.

How They Work

The central operation is nearest-neighbour search: given a query vector, find the stored vectors closest to it by a distance measure such as cosine similarity. Doing this exactly across millions of high-dimensional vectors would be far too slow, so vector databases use Approximate Nearest Neighbour (ANN) algorithms — such as HNSW — that trade a tiny amount of accuracy for enormous speed. They also add the practical machinery of a real database: indexing, filtering by metadata, updates, scaling and persistence.

Traditional vs Vector Databases

Aspect Traditional (relational) Vector
Search type Exact / keyword match Similarity by meaning
Stores Rows and columns High-dimensional vectors
Best for Structured, transactional data Semantic search, RAG, recommendation

The Landscape

Options range from dedicated vector databases (such as Pinecone, Weaviate, Milvus, Qdrant and Chroma) to vector capabilities added onto tools you may already run — for example the pgvector extension for PostgreSQL, vector search in Elasticsearch/OpenSearch, or managed offerings like Azure AI Search. For many organisations, adding vector search to an existing database is the lowest-friction starting point.

IT Director Considerations

  • Whether to adopt a dedicated vector database or extend an existing one (e.g. pgvector)
  • Managed service versus self-hosted, weighing control against operational burden
  • Scale and cost as the volume of embedded content grows
  • Access control and security on retrieved content, which RAG will surface to users
  • Integration with the wider data platform and AI tooling
  • Avoiding over-engineering — small use cases may not need a separate database at all

Vector Databases in the AI Stack

A vector database is the middle link in a chain. Embeddings turn content into vectors; the vector database stores and rapidly searches them by similarity; and RAG uses that search to feed an LLM the most relevant content at query time. The vector database is the retrieval engine that makes "chat with our documents" and semantic search fast and scalable.
