Docker

The platform that popularised containers – packaging applications into portable, consistent images

Overview

Docker is the platform that brought containers into the mainstream. It packages an application together with everything it needs to run — code, runtime, libraries and configuration — into a portable image that behaves the same way on a developer's laptop, a test server or production. By solving the long-standing "it works on my machine" problem, Docker became the de facto standard for building and running containers and a cornerstone of modern application delivery.

Core Components

  • Docker Engine — the runtime (the dockerd daemon) that builds and runs containers on a host.
  • Docker CLI — the command-line tool developers use to build, run and manage images and containers.
  • Docker Desktop — the packaged developer environment for Windows and macOS, bundling the engine and tooling.
  • Image & container — an image is the immutable template; a container is a running instance of that image.

Images & Dockerfiles

Docker images are built from a Dockerfile — a simple text recipe describing how to assemble the application environment step by step. Each instruction creates a layer, and layers are cached and reused, which makes rebuilds fast and images efficient to store and ship. Finished images are pushed to a registry — Docker Hub is the public default, while most organisations run a private registry (or use one built into their cloud) to control and secure their images.

Docker Compose

Real applications rarely consist of a single container. Docker Compose lets you define a multi-container application — for example a web app, its database and a cache — in a single YAML file, then start the whole stack with one command. It is widely used for local development and testing, where it provides a quick, reproducible environment without the complexity of full orchestration.

Where Docker Fits

Need Tool
Build and run containers Docker Engine + CLI
Local multi-container dev Docker Compose
Run at scale in production Kubernetes (orchestration)

Docker is excellent for building images and running containers on a host, but it is not an orchestrator. Once you need to run containers across many machines with scaling, self-healing and rolling updates, that job belongs to Kubernetes.

Security Considerations

  • Image provenance — base images can carry vulnerabilities or malicious content; use trusted sources and scan images.
  • Registry control — host a private registry with access control rather than pulling freely from public sources.
  • Least privilege — avoid running containers as root, and limit capabilities and host mounts.
  • Patching — images are point-in-time; rebuild and redeploy to pick up security fixes rather than patching in place.

IT Director Considerations

  • Docker Desktop licensing — it requires a paid subscription for commercial use above a company-size threshold, so confirm current terms before standardising on it
  • Image supply-chain security and scanning as part of the build pipeline
  • Private registry strategy and integration with CI/CD
  • The boundary between development (Docker, Compose) and production (orchestration)
  • Skills and standards, so teams build images consistently and securely
  • Open alternatives (such as Podman) where licensing or rootless operation matters

Docker vs Containers

Containers are the underlying concept — a standardised way of packaging and isolating applications using features of the host operating system. Docker is the best-known implementation of that concept: the tooling that builds and runs them. Thanks to open standards (the OCI), Docker images run on other runtimes too, and platforms like Kubernetes no longer require Docker specifically. In short: containers are the idea and the standard; Docker is the popular toolset that made them easy.
