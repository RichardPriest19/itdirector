Puppet

Declarative, model-driven configuration management that continuously enforces desired state

Overview

Puppet is a configuration management tool built around a declarative, model-driven philosophy: you describe the desired end state of a system — which packages, files, services and settings should exist — and Puppet works out how to make reality match, then keeps it that way. This emphasis on continuously enforcing a defined state makes Puppet especially strong for large, long-lived infrastructure and for compliance, where preventing configuration drift matters. First released in 2005 and written in Ruby, Puppet is now owned by Perforce.

How It Works

Puppet traditionally uses an agent-based, pull model. An agent installed on each managed node periodically checks in with a central Puppet server, which compiles a catalogue describing that node's desired state. The agent then enforces the catalogue locally and reports back. Because this cycle repeats on a schedule, any drift — a manual change, a setting that was altered — is automatically corrected on the next run. (A masterless mode is also possible for simpler setups.)

Core Concepts

  • Manifest — a file written in Puppet's declarative language defining resources.
  • Resource — a managed element such as a package, file, user or service.
  • Module / class — reusable, organised collections of related configuration.
  • Facter — gathers "facts" about each node (OS, IP, hardware) to inform decisions.
  • Hiera — separates configuration data from code, so the same logic serves many environments.
  • Puppet Forge — the public repository of community and vendor modules.

Strengths & Use Cases

  • State enforcement — continuously corrects drift, ideal for stable, regulated environments.
  • Scale — proven across very large fleets of servers.
  • Compliance — a strong fit where systems must demonstrably stay in a known-good state.
  • Maturity — a large module ecosystem and a long operational track record.

IT Director Considerations

  • The learning curve of Puppet's own declarative language compared with YAML-based tools
  • Infrastructure overhead of running and maintaining a Puppet server and agents
  • Best fit for relatively stable, long-lived estates rather than highly ephemeral cloud workloads
  • Value of automatic drift correction for compliance and audit evidence
  • Skills availability, given Ansible's rise has shifted much of the market's attention
  • How Puppet sits alongside provisioning tools like Terraform that create the infrastructure it then manages

Puppet vs Ansible & Chef

Puppet is declarative and agent-based: you model the desired state and agents pull and enforce it on a schedule, automatically correcting drift — excellent for large, stable estates and compliance, at the cost of more setup and a dedicated language to learn. Ansible is agentless and push-based using simple YAML, making it quicker to adopt and more versatile beyond configuration management. Chef shares Puppet's agent-based, pull model but takes a more code-centric approach using a Ruby-based language. A rough rule of thumb: Puppet for declarative state enforcement at scale, Ansible for breadth and ease of adoption, Chef for code-heavy teams comfortable with Ruby.
