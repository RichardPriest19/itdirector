Git & Version Control

Tracking changes to code and files over time – the foundation of modern software collaboration

Overview

Version control is the practice of recording changes to files over time so you can see what changed, when, why and by whom — and roll back if needed. For software, it is non-negotiable: it enables many people to work on the same codebase without overwriting each other, preserves a complete history, and underpins automation. Git is the dominant version control system by a wide margin. Created by Linus Torvalds in 2005 for the Linux kernel, it is a distributed system, meaning every copy of a repository contains the full project history rather than depending on a central server.

Centralised vs Distributed

Aspect Centralised (e.g. SVN) Distributed (Git)
History location On a central server Full copy in every clone
Offline work Limited Full commit/history offline
Resilience Server is a single point of failure Every clone is effectively a backup

Core Concepts

  • Repository — the project and its complete history.
  • Commit — a recorded snapshot of changes, with an author and message.
  • Branch — an independent line of work that can develop separately from the main code.
  • Merge — bringing changes from one branch into another.
  • Clone / pull / push — copying a repository and syncing changes with a remote copy.
  • Staging area — where changes are gathered before being committed.

Branching & Workflows

Cheap, fast branching is Git's defining strength: teams create a branch per feature or fix, work in isolation, then merge back. Different teams formalise this in different ways:

  • Trunk-based development — short-lived branches merged frequently into one main line; favoured for continuous delivery.
  • GitHub Flow — a simple branch-and-pull-request model.
  • Gitflow — a more structured model with dedicated release and hotfix branches, suited to scheduled releases.

Why It Matters

  • Collaboration — many contributors working safely on the same codebase.
  • History & audit — a complete, attributable record of every change.
  • Safety — the ability to revert to any previous state.
  • Automation foundation — CI/CD pipelines trigger from commits, making Git the entry point to DevOps.
  • Beyond code — increasingly used for infrastructure (IaC), configuration and documentation.

IT Director Considerations

  • Standardising on Git as the single version-control system across teams
  • Agreeing a branching strategy that fits your release cadence and governance
  • Preventing secrets (passwords, keys) from being committed, and scanning for them
  • Repository governance — access, ownership, naming and retention
  • Backup and continuity, even though distribution provides natural redundancy
  • Training, since Git's power comes with a genuine learning curve

Git vs GitHub / GitLab

Git is the underlying tool — the version-control engine that runs on developers' machines and servers, with no web interface of its own. GitHub and GitLab are platforms built around Git that add hosting, code review, automation, security and project management. You can use Git entirely without them, but in practice most organisations pair Git with a platform to enable team collaboration at scale. In short: Git is the technology; GitHub and GitLab are services built on it.
