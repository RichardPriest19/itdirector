Load Balancing

Distributing traffic across multiple servers to improve performance, scalability and resilience

Overview

Load balancing is the practice of distributing incoming requests across a pool of backend servers so that no single server becomes a bottleneck or a single point of failure. It is a foundational technique behind almost every scalable, highly available service: rather than relying on one large server, traffic is spread across many, and the load balancer presents them to users as a single endpoint. The result is better performance, the ability to scale out, and resilience when individual servers fail.

How It Works

Clients connect to a single virtual address presented by the load balancer, which then forwards each request to one of several backend servers (often called a pool or server farm). The load balancer continuously runs health checks against those servers and stops sending traffic to any that fail, routing around problems automatically. Because state can be an issue when a user's requests land on different servers, load balancers can maintain session persistence ("stickiness") so a given client keeps hitting the same backend where required.

Common Algorithms

  • Round robin — each server in turn; simple and even when servers are equal.
  • Least connections — favour the server currently handling the fewest sessions.
  • Weighted — send more traffic to more capable servers.
  • IP hash — map a client consistently to the same server based on its address.
  • Least response time — factor in how quickly servers are currently responding.

Where It Is Used

  • Web and application tiers — spreading user traffic across server farms.
  • Global load balancing (GSLB) — directing users to the best site or region, often via DNS.
  • Cloud-native — managed load balancers and ingress controllers in front of containers and Kubernetes services.
  • Application delivery controllers (ADCs) — combining load balancing with SSL offload, caching and security.

IT Director Considerations

  • Resilience: the load balancer itself must be redundant, or it becomes the single point of failure it was meant to remove
  • Hardware appliance vs software vs cloud-managed load balancing, and the cost and flexibility trade-offs
  • SSL/TLS termination and certificate management as a central responsibility
  • Integration with autoscaling so capacity follows demand
  • Observability — health checks, metrics and logging to understand traffic and failures
  • Security features such as WAF and rate limiting often delivered at this tier

Load Balancing vs Failover

The two are related but distinct. Load balancing actively distributes traffic across multiple servers that are all in use, improving both performance and availability. Failover keeps a standby resource idle until the primary fails, addressing availability alone. Load balancing effectively delivers failover as a by-product — because unhealthy servers are simply removed from the pool — which is why it underpins most modern high-availability and horizontal-scaling designs.
