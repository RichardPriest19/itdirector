BGP

Border Gateway Protocol – the path-vector routing protocol that holds the internet together

Overview

BGP (Border Gateway Protocol) is the routing protocol that exchanges reachability information between the large, independently operated networks that make up the internet. Each of these networks is an Autonomous System (AS) with its own number, and BGP is how they tell one another which destinations they can reach and by what path. Defined in RFC 4271 (BGP-4), it runs over TCP port 179, which gives it reliable, ordered delivery of routing updates. BGP is described as a path-vector protocol because it advertises the full list of autonomous systems a route passes through, which is central to both loop prevention and policy.

eBGP vs iBGP

BGP runs in two contexts that behave differently:

Aspect eBGP (External) iBGP (Internal)
Peers Between different autonomous systems Between routers in the same AS
Typical use Connecting to ISPs and peers Carrying external routes across the AS
Scale aid Direct peering sessions Route reflectors or confederations

Path Selection

Unlike interior protocols that simply pick the shortest path, BGP chooses routes using a ranked list of attributes, which lets operators steer traffic for commercial and engineering reasons rather than purely on distance:

  • Weight (Cisco-specific, local to one router) and Local Preference (consistent across the AS) — the primary levers for preferring one exit over another.
  • AS_PATH — a shorter list of autonomous systems is preferred, and it doubles as the loop-prevention mechanism.
  • MED (Multi-Exit Discriminator) — a hint to a neighbouring AS about a preferred entry point.
  • Communities — tags attached to routes to apply policy at scale.

Where It Is Used

  • Internet edge / multihoming — connecting an enterprise to two or more ISPs for resilience and traffic control.
  • Service providers — carrying the full internet routing table (well over a million IPv4 prefixes).
  • MPLS VPNs — MP-BGP distributes customer VPN routes across provider networks.
  • Data centre fabrics — eBGP is increasingly used as the control plane in leaf-spine (Clos) designs.

Security Considerations

BGP was designed for a smaller, higher-trust internet, and by default it accepts what peers advertise. This has led to repeated high-profile outages from route hijacks and leaks. Key controls:

  • Prefix filtering — only accept and announce expected prefixes from each peer.
  • RPKI / ROAs — Resource Public Key Infrastructure lets networks cryptographically validate which AS is authorised to originate a prefix.
  • Maximum-prefix limits — guard against a misbehaving peer flooding the routing table.
  • MANRS — an industry set of routing-security norms many providers commit to.

IT Director Considerations

  • ISP multihoming strategy and whether to obtain a public ASN and provider-independent address space
  • The difference between transit and peering, and its cost and resilience implications
  • Dependence on provider routing hygiene; questions to ask ISPs about RPKI and filtering
  • DDoS response options that rely on BGP, such as remotely triggered blackholing and traffic scrubbing
  • Monitoring and alerting for prefix hijacks and unexpected route changes
  • BGP as a data-centre control plane, and the skills implications of that choice

BGP vs OSPF

Use BGP where you need to exchange routes between organisations or sites under different administrative control — the internet edge, provider networks, and large fabrics — and where policy and scale matter more than raw convergence speed. Use an interior protocol such as OSPF inside a single network you fully control, where fast convergence on the shortest path is the priority. In practice the two are complementary: OSPF (or another IGP) runs the inside, BGP handles the boundaries.
