Containers

Containerization – lightweight, portable packaging and isolation of applications using the host OS

Overview

Containerization is a way of packaging an application together with its dependencies into a single, portable unit that runs reliably across different environments. Unlike virtual machines, containers do not each carry a full operating system — they share the host's OS kernel while remaining isolated from one another. This makes them lightweight, fast to start, and dense, allowing far more workloads to run on the same hardware. Containers have become the default packaging model for modern, cloud-native applications.

Containers vs Virtual Machines

Aspect Containers Virtual Machines
Isolation boundary Share the host OS kernel Each runs its own full OS
Size & startup Megabytes; start in seconds Gigabytes; start in minutes
Density Many per host Fewer per host
Isolation strength Lighter (shared kernel) Stronger (hardware-level)

How They Work

Containers rely on features built into the Linux kernel. Namespaces give each container its own isolated view of the system — its own processes, network and file system — so it cannot see others. Control groups (cgroups) limit and account for the resources (CPU, memory) a container can consume. A layered, copy-on-write file system lets containers share common layers efficiently while keeping their own changes separate. Together these provide isolation without the overhead of a separate operating system per workload.

Standards & Runtimes

Containerization is built on open standards, which is why it is not tied to any single vendor:

  • OCI (Open Container Initiative) — defines standard formats for images and runtimes, ensuring portability.
  • containerd — a widely used core runtime that manages container lifecycle, used by many platforms.
  • runc — the low-level runtime that actually creates and runs containers.
  • Alternatives — tools such as Podman and CRI-O provide OCI-compatible options beyond Docker.

Why It Matters

  • Portability — the same image runs consistently from laptop to cloud.
  • Efficiency — high density and fast startup reduce infrastructure cost.
  • Consistency — eliminates environment drift between dev, test and production.
  • Foundation for microservices — small, independently deployable services map naturally to containers.

Orchestration at Scale

Running a handful of containers on one host is straightforward; running hundreds across many machines is not. That is the role of orchestration — most commonly Kubernetes — which handles scheduling, scaling, self-healing, networking and rolling updates. For most organisations, adopting containers seriously means adopting an orchestration platform alongside them, with the operational skills that implies.

Security Considerations

  • Shared-kernel risk — isolation is weaker than VMs, so a kernel vulnerability has a wider blast radius.
  • Image vulnerabilities — scan images and use minimal, trusted base layers.
  • Least privilege — avoid running as root; consider rootless containers and tight resource limits.
  • Runtime security — monitor running containers for unexpected behaviour, not just images at build time.

IT Director Considerations

  • Application modernisation strategy and where containers fit versus VMs and serverless
  • The operational and skills investment that orchestration (Kubernetes) demands
  • Security posture across the full lifecycle — build, registry, deploy and runtime
  • Avoiding lock-in by leaning on open standards (OCI) rather than a single vendor's tooling
  • Sensitivity of workloads — where stronger VM-level isolation is still warranted
  • Governance of images, base layers and supply chain across teams

Containers vs Docker

Containers are the concept and the open standard — a lightweight way of packaging and isolating applications using the host operating system. Docker is the best-known toolset for building and running them, and the product that made the idea mainstream. Because of open standards, containers run on many runtimes beyond Docker. In short: containers are the idea; Docker is one popular way to work with them.
