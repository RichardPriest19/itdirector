Ansible

Agentless automation and configuration management using simple, human-readable YAML

Overview

Ansible is an automation tool used for configuration management, application deployment, provisioning and orchestration. Its defining characteristic is that it is agentless: it needs no software installed on the machines it manages, connecting instead over standard SSH (or WinRM for Windows). Combined with its use of simple, human-readable YAML, this gives Ansible the lowest barrier to entry of the major configuration tools, which is a large part of why it has become the most widely adopted. Created by Michael DeHaan and acquired by Red Hat in 2015, it now sits within IBM's Red Hat portfolio.

How It Works

Ansible follows a push model: a control node connects out to the managed machines listed in an inventory and applies the desired configuration. There is no central server or database required for basic use, and no persistent agent polling for changes. Operations are idempotent — running the same playbook repeatedly converges the system to the defined state without making redundant changes — so playbooks are safe to re-run.

Core Concepts

  • Playbook — a YAML file describing the desired configuration as a series of plays and tasks.
  • Module — a unit of work (install a package, copy a file, manage a service); Ansible ships with thousands.
  • Inventory — the list of managed hosts, which can be static or generated dynamically (e.g. from a cloud).
  • Role — a reusable, shareable bundle of tasks, variables and files.
  • Ansible Galaxy — the public hub for sharing roles and collections.
  • Ansible Vault — built-in encryption for secrets such as passwords and keys.

Strengths & Use Cases

  • Low barrier to entry — agentless and YAML-based, easy for mixed teams to pick up.
  • Versatile — handles config management, app deployment, cloud provisioning and orchestration in one tool.
  • Network & appliance automation — strong support for devices that cannot run an agent.
  • Ad-hoc tasks — quick one-off commands across many machines without writing a full playbook.

For larger organisations, the commercial Ansible Automation Platform adds a web UI, role-based access control, scheduling, credentials management and auditing on top of the open-source engine.

IT Director Considerations

  • Fast time-to-value thanks to the agentless model and gentle learning curve
  • The push model's reliance on network reachability and SSH access to targets
  • When to step up from open-source Ansible to the supported Automation Platform for governance at scale
  • Secrets management discipline (Vault) so credentials never sit in plain text
  • How Ansible complements provisioning tools like Terraform rather than replacing them
  • Standardising reusable roles to avoid duplicated, drifting automation across teams

Ansible vs Puppet & Chef

Ansible is agentless and push-based, using YAML — generally the simplest of the three to start with and the most versatile beyond pure configuration management. Puppet and Chef are agent-based and pull-based, with each managed node running an agent that periodically fetches and enforces its desired state from a central server. That model excels at continuously correcting drift across large, long-lived server fleets, but carries more setup and a steeper learning curve. A rough rule of thumb: Ansible for breadth and quick adoption, Puppet for declarative state enforcement at scale, Chef for code-centric teams comfortable with Ruby.
